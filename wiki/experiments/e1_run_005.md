# E1 run 005 — IVF with nprobe = 16

The candidate best trade-off point of the sweep. Source: `experiments/results/run_e1_005/metrics.json`.

## Hypothesis

`faiss_ivf` with `nprobe = 16` keeps Recall@10 within 2 points of exact search while cutting p95
latency by at least 3×.

## Config diff vs run_e1_004

One factor changed: `nprobe: 4` → `nprobe: 16`. `nlist` stays 240.

## Metrics (57,638 docs, 500 queries, dim 384)

| Metric | run 001 (exact) | run 005 (nprobe 16) | Gap |
|---|---|---|---|
| Recall@5 | 0.3797 | 0.3542 | −2.55 pt |
| Recall@10 | 0.4665 | 0.4383 | **−2.82 pt** |
| MRR@10 | 0.4532 | 0.4277 | −2.55 pt |
| nDCG@10 | 0.3881 | 0.3631 | −2.51 pt |
| latency mean | 0.6704 ms | 0.0892 ms | 7.5× faster |
| latency p95 | 0.7674 ms | 0.1065 ms | **7.2× faster** |
| build time | 0.00053 s | 0.1829 s | — |

## Verdict

**Partly confirmed.** The speed claim holds comfortably: 7.2× faster on p95, well beyond the 3× bar.
The accuracy claim misses: the gap is 2.82 points, not ≤2.

## Interpretation

This is the knee of the curve: 4 → 16 cells costs 3× the latency but buys back 6.5 points of
Recall@10 (−9.32 → −2.82). Whether 2.82 points is acceptable depends on what E3 does with it —
a retrieval loss of under 3 points combined with a 7× speed-up is defensible, but it has to be
checked against answer quality, not asserted here.
