# E1 run 002 — FAISS Flat control

Correctness control: a library exact index must return the **same** top-10 as our own `TorchKNN`.
Only latency should differ. Source: `experiments/results/run_e1_002/metrics.json`.

## Hypothesis

`faiss_flat` returns the same top-10 as `torch_knn`, so Recall@10 is identical; the difference is
purely per-query latency.

## Config diff vs run_e1_001

One factor changed: `method: torch_knn` → `method: faiss_flat`. Everything else identical.

## Metrics (57,638 docs, 500 queries, dim 384)

| Metric | run 001 | run 002 |
|---|---|---|
| Recall@5 | 0.3797 | 0.3797 |
| Recall@10 | 0.4665 | 0.4665 |
| MRR@10 | 0.4532 | 0.4532 |
| nDCG@10 | 0.3881 | 0.3881 |
| latency mean | 0.6704 ms | 1.1289 ms |
| latency p95 | 0.7674 ms | 1.2350 ms |
| build time | 0.00053 s | 0.0350 s |
| index memory | 84.43 MB | 84.43 MB |

## Verdict

**Accuracy half confirmed.** All four accuracy metrics are bit-identical, which validates our
`TorchKNN` against a reference implementation.

The speed half of the hypothesis was **inconclusive as measured and settled by a follow-up
measurement** (below): under the single-thread workaround FAISS Flat looked 1.7× *slower* than our
PyTorch code; at natural thread counts the two are within 8%, i.e. a tie.

## Re-measurement at natural thread counts (2026-10-28)

`run_e1_002` was measured under `KMP_DUPLICATE_LIB_OK=TRUE OMP_NUM_THREADS=1`, the macOS workaround
for the duplicate-OpenMP clash. That caps FAISS at one thread, so we re-timed both back ends in
processes that import only the library they need (FAISS: `scripts/bench_faiss_isolated.py`; torch:
`run_experiment.py` with no env vars). Same protocol otherwise.

| Method | p95, single thread | p95, natural threads |
|---|---|---|
| torch_knn | 0.7674 ms | 0.7645 ms |
| faiss_flat | 1.2350 ms | 0.8285 ms |

The 1.7× gap shrinks to 1.08×. Two exact implementations of the same O(N·d) scan coming out within
8% is the expected result, and it is what the report should say. The gain comes almost entirely from
FAISS Flat touching the whole 84 MB corpus per query — the IVF back ends gained nothing from extra
threads (see [e1_summary](e1_summary.md)).
