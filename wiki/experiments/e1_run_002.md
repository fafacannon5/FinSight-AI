# E1 run 002 — FAISS Flat control

Correctness control: a library exact index must return the **same** top-10 as our own `TorchKNN`.
Only latency should differ. Source: `experiments/results/run_e1_002/metrics.json`.

## Hypothesis

`faiss_flat` returns the same top-10 as `torch_knn`, so Recall@10 is identical; the difference is
purely per-query latency.

## Config diff vs run_e1_001

One factor changed: `method: torch_knn` → `method: faiss_flat`. Everything else identical.

## Metrics (57,638 docs, 500 queries, dim 384)

| Metric | run 001 | run 002 |
|---|---|---|
| Recall@5 | 0.3797 | 0.3797 |
| Recall@10 | 0.4665 | 0.4665 |
| MRR@10 | 0.4532 | 0.4532 |
| nDCG@10 | 0.3881 | 0.3881 |
| latency mean | 0.6704 ms | 1.1289 ms |
| latency p95 | 0.7674 ms | 1.2350 ms |
| build time | 0.00053 s | 0.0350 s |
| index memory | 84.43 MB | 84.43 MB |

## Verdict

**Accuracy half confirmed, speed half rejected.** All four accuracy metrics are bit-identical, which
validates our `TorchKNN` against a reference implementation. But FAISS Flat is **1.7× slower** than
our PyTorch code, not faster.

## Interpretation (important for the report)

This is the one number that must not be reported naively. `faiss_flat` was forced to a single thread
by the macOS workaround (`OMP_NUM_THREADS=1`), while the search itself is memory-bandwidth bound:
our torch baseline barely changes between 1 and 5 threads (0.608 vs 0.603 ms measured separately).
So the 1.7× gap is a property of the constrained environment, not evidence that FAISS is slow.
Latency figures need a re-run on a clean install before they go into the report; the **accuracy**
numbers are unaffected.

## Next step

Re-measure latency after installing `faiss-cpu` from conda-forge (single shared OpenMP runtime),
then repeat runs 001–002 to confirm the timing story.
