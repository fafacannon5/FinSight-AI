# E1 run 001 — FiQA dev baseline

Baseline for every later E1 run: our own exact PyTorch brute-force KNN on the full FiQA corpus.
Source: `experiments/results/run_e1_001/metrics.json`.

## Hypothesis

Exact PyTorch KNN on FiQA dev is the reference point; accuracy of every approximate method is
measured as the gap to this run, and speed as the ratio against this run.

## Config

`experiments/configs/run_e1_001.yaml` — dataset `fiqa`, split `dev`, method `torch_knn`,
`k` 10, `latency_queries` 200, seed 42. No PCA, full corpus.

## Metrics (57,638 docs, 500 queries, dim 384)

| Metric | Value |
|---|---|
| Recall@5 | 0.3797 |
| Recall@10 | 0.4665 |
| MRR@10 | 0.4532 |
| nDCG@10 | 0.3881 |
| latency mean | 0.6704 ms |
| latency p95 | 0.7674 ms |
| build time | 0.00053 s |
| index memory | 84.43 MB |

## Verdict

**Baseline established.** FiQA is much harder than SciFact: Recall@10 0.4665 here vs 0.7833 on the
SciFact smoke run, so the smoke numbers must never be quoted as results.

## Notes

- `build_time_s` = 0.00053 s is only the numpy → tensor copy; exact search has no preprocessing.
- `index_memory_mb` = 84.43 = 57,638 × 384 × 4 / 2²⁰ — payload only, no index structure.
- Measured with `OMP_NUM_THREADS=1` (macOS OpenMP workaround). A separate check showed torch takes
  0.603 ms at 5 threads vs 0.608 ms at 1 thread for this matmul, so the workaround barely affects
  this number: single-query search over 84 MB is memory-bandwidth bound, not compute bound.
