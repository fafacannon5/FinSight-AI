# E1 run 006 — IVF with nprobe = 64

Upper end of the planned grid: 64 of 240 cells ≈ 27% of the corpus visited per query.
Source: `experiments/results/run_e1_006/metrics.json`.

## Hypothesis

`faiss_ivf` with `nprobe = 64` is within 1 point of exact Recall@10, but its latency advantage
shrinks towards exact search.

## Config diff vs run_e1_005

One factor changed: `nprobe: 16` → `nprobe: 64`. `nlist` stays 240.

## Metrics (57,638 docs, 500 queries, dim 384)

| Metric | run 001 (exact) | run 006 (nprobe 64) | Gap |
|---|---|---|---|
| Recall@5 | 0.3797 | 0.3797 | 0.00 pt |
| Recall@10 | 0.4665 | 0.4665 | **0.00 pt** |
| MRR@10 | 0.4532 | 0.4532 | −0.00 pt (3.6e−5) |
| nDCG@10 | 0.3881 | 0.3882 | +0.00 pt |
| latency mean | 0.6704 ms | 0.3254 ms | 2.1× faster |
| latency p95 | 0.7674 ms | 0.3659 ms | 2.1× faster |
| build time | 0.00053 s | 0.1826 s | — |

## Verdict

**Confirmed on both halves.** Recall@10 is identical to exact search to 15 decimal places (MRR
differs by 3.6e−5, i.e. one rank swap deep in the list), and the speed-up has fallen from 7.2×
(nprobe 16) to 2.1×.

## Interpretation

Searching 27% of the corpus already reproduces exact top-10 — the last 73% of the data changes
nothing about the ranking. This is the strongest evidence that the accuracy loss at low `nprobe`
comes from *cell assignment*, not from the number of vectors scored: a query's true neighbours sit
in a few cells, and once those cells are visited the result is exact.
